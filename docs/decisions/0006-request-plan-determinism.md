# 0006: Request-plan determinism for load generation

- **Status:** Accepted
- **Date:** 2026-10-24

## Context

The M4 roadmap requires `pnpm loadgen --profile steady --seed 42` to produce "the same request sequence on every run". M5 builds on that: an incident must be reproducible from a scenario name and a seed, and the traffic is part of the scenario.

Several parts of a load run cannot repeat exactly. Order ids are generated by the server. Responses depend on database state, such as stock and earlier orders, and on the worker's progress. Send times and latencies vary from run to run. Idempotency keys that repeated across runs would turn a second run into replays of the first run's orders. The full design is `docs/prompts/m4-design.md`.

## Decision

- **Determinism means the request plan.** A run's canonical request plan is a pure function of the profile and seed. Each entry has an index, a scheduled offset, an operation, and its parameters.
- **References, not ids.** A request that needs a server-generated value, such as reading an order, refers to the plan index of the request that produces it. The id is resolved at runtime.
- **The plan is hashed.** The plan hash is SHA-256 over the canonical plan text. Responses, server ids, actual send times, latencies and the per-run idempotency prefix are excluded.
- **Seeded randomness.** It comes from a small PRNG in the package, with no new dependency and with fixed test vectors. Each decision dimension gets its own stream derived from the seed.
- **Per-run uniqueness lives outside the plan.** Idempotency keys combine a unique per-run prefix with the plan index, so runs never collide and the hash is unaffected.
- **Database state is checked, never changed.** Before a live run, a preflight through the orders API's public endpoints confirms readiness, the catalog, and a starting stock shortfall of at most 5% of the plan's order-item quantity. It cannot guarantee stock during the run, because orders and the worker change inventory. The load generator never resets or reseeds the database.

## Consequences

- **Positive:** "Same request sequence" is testable in CI, without a database, by comparing plan hashes with a committed golden value.
- **Positive:** M5 bundle manifests can record the profile, seed and plan hash as reproducible ground truth for the traffic.
- **Negative:** Two runs with the same plan can see different responses, for example once stock runs out. Comparisons across runs must account for database state.
- **Negative:** Any change to plan generation changes the golden hash. That is intended, but it needs a deliberate test update and a note in the change.
- **Revisit if:** M5 needs response-level reproducibility, which would require a database snapshot or reset per run, or a profile needs closed-loop behavior that depends on responses.
