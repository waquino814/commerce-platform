# M4 design: load generation

Status: **approved.** Every design choice below has been resolved with the repository owner. **Done: implemented in commit `5f6f6eb`, green in GitHub Actions as confirmed by the repository owner, and all 12 acceptance criteria pass. Criterion 11 passed on its first run: 55.00 rps with a load-generator p95 of 8.2 ms and a 0% failure rate. The results are recorded in `docs/roadmap.md`.** The determinism decision is recorded in ADR 0006.

## Scope

**In scope:**

- an `apps/loadgen` workspace app with seeded, deterministic traffic profiles against the orders API, starting with `steady`;
- a `pnpm loadgen` CLI that runs on the host against a running API;
- a per-run report of offered, sent, successful, failed, missed and skipped counts, throughput, failure rate and latency, plus the preflight results;
- deterministic tests in CI, and a local-only performance check.

**Out of scope:**

- fault injection, scenarios and incident bundles (M5), and any UI (M7);
- a telemetry SDK in the load generator, and a Compose service for it;
- any change to the API, the worker, the database schema or M2 and M3 behavior. The only functional change outside `apps/loadgen` is a pure catalog export from `packages/db`, described below. Repository wiring also changes, without changing behavior: the Docker build stage, the TypeScript project references, the lint config, the Vitest aliases and coverage gate, the root `loadgen` and `test:smoke` scripts, and `.env.example`;
- automatic database resets.

## Sources

**Specified by repository docs:**

- **Roadmap, M4:** `pnpm loadgen --profile steady --seed 42` produces the same request sequence on every run. The steady profile sustains at least 50 requests per second locally, with p95 latency under 200 ms and an error rate under 1%.
- **Architecture:** `apps/loadgen` runs seeded, deterministic traffic profiles against the orders API and does not inspect internal state. Traffic flows `loadgen -> orders-api`.
- **CLAUDE.md:** local only, with no cloud services or paid APIs. Apps are built through factory functions that receive their dependencies, including the clock and random source. Config is validated with Zod and fails fast. New behavior needs tests. Dependencies stay small and are justified.
- **ADR 0001:** reproducibility from a name and a seed.

**Approved by the repository owner for this proposal:**

- request-plan determinism (ADR 0006), with mulberry32 and splitmix32 stream derivation and no new dependency;
- the `steady` profile at 55 offered requests per second, with a 60/25/15 mix and uniform SKU selection;
- per-run idempotency prefixes, and no automatic reset or reseed;
- a 5 s warm-up and a 60 s measured window;
- open-loop scheduling with a 64-request in-flight cap;
- separate counts for offered, sent, successful, failed, missed and skipped requests;
- a preflight before every live run: the orders API's `/readyz` only, the catalog, and a starting stock shortfall of at most 5% of planned order-item quantity;
- a host-run CLI with no telemetry SDK;
- deterministic tests and a 2 s, 20 rps functional test on isolated test data in CI, and the performance check local-only;
- a pure catalog export from `@commerce/db/catalog`, as preferred;
- the `steady` parameters: product-list `limit` 20 with no cursor 10% of the time, 1 to 3 distinct SKUs per order with quantity 1 or 2, a 92/8 `pm_card_ok`/`pm_card_declined` mix, and order reads that target a create scheduled at least 1 s earlier;
- a 100 ms missed-deadline tolerance;
- a CI functional test that reuses the existing in-process API pattern, with isolated test data;
- a per-SKU shortfall listing in the preflight report, next to the aggregate.

## API facts the design relies on

- `GET /products?limit=&after=` pages the catalog by SKU, with `limit` from 1 to 100 and `after` a SKU of the form `SKU-#####`. It returns `{ items, nextCursor }`.
- `POST /orders` takes `{ items: [{ sku, quantity }], paymentMethod }`, with quantity from 1 to 100 and distinct SKUs. It returns 201 for a new order, 200 with `Idempotent-Replayed: true` for a replayed `Idempotency-Key`, 409 for a key reused with a different body, and 422 for unknown SKUs. A key is 1 to 128 visible ASCII characters.
- `GET /orders/:id` returns 200, or 404 for an unknown id. Order ids are generated by the server.
- Stock is reserved by the worker, not the API. An order for an out-of-stock SKU is still accepted with 201 and later fails with `out_of_stock`.
- The seed catalog is 1,000 products, `seedProduct(1)` to `seedProduct(1000)`, with 108,570 units in total. Every 100th SKU has 3 units; the others have 20 to 199. `pnpm db:seed` never changes existing SKUs, so it never restores stock.
- The API uses one pool with pg's default of 10 connections.

## Determinism: the request plan

A **request plan** is a pure function of the profile and the seed. See ADR 0006.

- **Entry:** `{ index, offsetMs, op, params }`, where `op` is `product.list`, `order.create` or `order.read`.
  - `product.list`: `limit` and `after`.
  - `order.create`: `items`, `paymentMethod` and `keyIndex`, the plan index used for its idempotency key.
  - `order.read`: `createIndex`, the plan index of an earlier `order.create`. The order id is resolved at runtime from that request's response.
- **Offsets:** `offsetMs = index * 1000 / rate`, so the schedule is exact and does not depend on timing.
- **Canonical form:** one JSON object per entry with keys in a fixed order, joined with newlines. The plan hash is SHA-256 over that text, from `node:crypto`.
- **Not hashed:** responses, server-generated ids, the run prefix, actual send times and latencies.
- **Dry run:** `pnpm loadgen --profile steady --seed 42 --dry-run` prints the entry count, the mix and the plan hash, and makes no network call.

**Seeded randomness.** A small PRNG written in the package, mulberry32, with 32-bit seeds. Each decision dimension gets its own stream, derived from the seed with splitmix32 and a fixed stream id: operation, SKU, quantity, payment method, cursor, read target and item count. Changing one dimension's logic then does not reshuffle the others. Fixed test vectors pin the generator's output. It is not cryptographic and is never used for anything security-related.

## The `steady` profile

| Property       | Value                                                                                                                                            |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Offered rate   | 55 requests per second, 10% above the 50 rps threshold, so a run with under 1% failures still clears it                                          |
| Duration       | 65 s: a 5 s warm-up, then a 60 s measured window; 3,575 plan entries                                                                             |
| Mix            | 60% `product.list`, 25% `order.create`, 15% `order.read`                                                                                         |
| `product.list` | `limit` 20; `after` absent with 10% probability, otherwise a uniformly chosen catalog SKU                                                        |
| `order.create` | 1 to 3 distinct SKUs, chosen uniformly from the 1,000 catalog SKUs; quantity 1 or 2 each                                                         |
| Payment method | 92% `pm_card_ok`, 8% `pm_card_declined`. No `pm_card_unavailable`: provider outages belong to M5 scenarios                                       |
| `order.read`   | a uniformly chosen earlier `order.create` scheduled at least 1 s before it. An entry with no eligible create becomes `product.list` at plan time |

**Catalog source: `@commerce/db/catalog`.** The plan takes its SKU list from the seed catalog's definition. The seed module's only import is a type from the pool module, which is erased at build time, so this needs no database connection and no `pg`.

- **Change:** a new `packages/db/src/catalog.ts` holds `SEED_PRODUCT_COUNT`, `SeedProduct`, `seedProduct` and `seedProducts`, moved unchanged from `seed.ts`. `seed.ts` re-exports them, so every existing import keeps working. `packages/db/package.json` gains a `./catalog` export, next to the existing `./config`.
- **Why a new module, not `seed.ts`:** `seed.ts` also contains `seedCatalog`, which writes to the database. The catalog subpath exposes only pure data.
- **Boundaries:** apps may depend on packages; the catalog is seed data that already lives in `packages/db`; it contains no SQL and no business rules. Reading a pure definition is not inspecting internal state, which the architecture rules out.
- **Behavior:** unchanged for the seed, the API and the worker.

## Runtime

**Idempotency.** Every `order.create` sends `Idempotency-Key: <runPrefix>-<keyIndex>`. The run prefix is `lg-` plus a UUID from an injected source, unique per run and excluded from the plan hash. Without it, a second run with the same seed would only replay the first run's orders. A 200 replay or a 409 is therefore unexpected and counts as failed.

**Scheduling: open loop.** Each entry is due at `start + offsetMs` on an injected monotonic clock, whatever the latency of earlier requests.

- At most 64 requests are in flight.
- An entry whose send would start more than 100 ms after its due time is a **missed deadline**: it is not sent, and it is counted separately. Usually the in-flight cap is full, but scheduler lag, such as a busy event loop, also counts even when slots are free. A send at exactly 100 ms is on time.
- An `order.read` whose create has failed or has not completed by its due time is **skipped**, and counted separately.
- Each request has a 5 s timeout, enforced with `AbortSignal.timeout`.
- HTTP uses Node's built-in `fetch`. CLI arguments use `node:util` `parseArgs`. No new dependency.

**Accounting.** Each plan entry due inside the measured window gets exactly one outcome.

| Outcome                                                                                      | Category   |
| -------------------------------------------------------------------------------------------- | ---------- |
| `product.list` 200, `order.create` 201, `order.read` 200                                     | successful |
| Any other status, including a 200 replay, 409, 404, 422 and 5xx                              | failed     |
| Transport failure, or no response within 5 s                                                 | failed     |
| Not started within 100 ms of its due time, whether the cap is full or the scheduler ran late | missed     |
| `order.read` whose create failed, was missed, or has not completed                           | skipped    |

The report gives each count separately. With every count taken over entries due in the window:

- **offered** = every entry due in the window, so offered = sent + missed + skipped;
- **sent** = successful + failed. The run waits for every sent request to finish or time out, so none is left pending;
- **throughput** = successful ÷ 60 s;
- **failure rate** = failed ÷ sent;
- **miss rate** = missed ÷ offered, and **skip rate** = skipped ÷ offered, both reported but not thresholds;
- **latency** = time from send to response on the monotonic clock, over every sent request. A timeout counts as 5,000 ms. The report gives p50, p95 and p99 by nearest rank, overall and per operation.

Warm-up entries and preflight requests are excluded from every count.

**Pass (local check):** throughput of at least 50 rps, p95 under 200 ms, and a failure rate under 1%. The roadmap's "error rate" is this failure rate. Missed and skipped entries are never successful, so they lower throughput. Exit code 0 on pass, 1 otherwise.

**Preflight.** Before any live run, and never in `--dry-run`, the load generator checks the target through the orders API's public endpoints only:

1. **Readiness:** `GET /readyz` on the orders API returns 200, which means the API can reach its database. Otherwise it exits 1 and suggests `docker compose up -d --build --wait`. Worker readiness is not checked and is not a prerequisite: the load generator targets the orders API, and its thresholds measure only the API's responses.
2. **Catalog match:** it pages `GET /products?limit=100` through the whole catalog. Every planned SKU must exist there. A missing SKU means the database was not seeded from the same catalog, and the run stops.
3. **Stock sufficiency:** from the same pages it reads each SKU's `stockAvailable`, then computes the stock shortfall:

   ```
   planned(sku)  = sum of quantity over every order.create item for that SKU, in the whole plan, warm-up included
   unmet(sku)    = max(0, planned(sku) - stockAvailable(sku))
   shortfall (%) = 100 * sum of unmet(sku) / sum of planned(sku), over all SKUs
   ```

   If the shortfall is above 5%, it exits 1. Exactly 5% passes. The threshold applies only to the aggregate.

   **Preflight report.** On pass and on fail, the report gives the aggregate shortfall with total planned and unmet quantities, and lists every SKU whose planned quantity exceeds its available stock, with `sku`, `planned`, `available` and `unmet`, sorted by `unmet` descending and then by SKU. The human-readable summary shows the first 20 of these SKUs and the total count; `--json` lists all of them under `preflight.stock.shortSkus`. On fail, the message also says that restoring stock means recreating the database by hand, because `pnpm db:seed` never changes existing SKUs. The per-SKU list is informational: a short SKU never fails the run by itself.

   **Why 5%:** with uniform SKU selection, the 10 scarce SKUs receive about 1% of the planned quantity and empty within a run or two, so a lower threshold would block runs on stock that is scarce by design. Out-of-stock orders still return 201, so they never affect the API thresholds.

**What the preflight can and cannot promise.** It validates readiness, the catalog and the stock available at the moment it runs. It cannot guarantee stock throughout the run: the run's own orders reserve stock, other clients may place orders, and the worker reserves and releases inventory concurrently. The calculation also treats all planned quantity as reserved, ignoring stock released by declined orders. The preflight is a guard against starting on a depleted database, not a reservation.

The preflight never writes, resets or reseeds anything. It sends only `GET` requests, before the run starts, and they are not part of the plan or the report's counts.

**Report.** A human-readable summary on stdout, or JSON with `--json`: profile, seed, plan hash, run prefix, the preflight results, and the counts, rates and latencies above. No files are written, consistent with not committing generated telemetry.

## Database-state assumptions

- **Determinism covers requests only.** Responses depend on the database: stock, earlier orders, and the worker's progress.
- **Stock use.** The steady/42 plan has 923 creates for 2,771 units, about 2.6% of the seed stock, or 2.8 units per SKU on average. Stock is consumed by paid orders and released by failed ones.
- **Scarce SKUs.** The 10 scarce SKUs, with 3 units each, run out within a run or two. Those orders still return 201 and fail in the worker with `out_of_stock`, which is a worker outcome, not a load-generator failure.
- **Repeated runs** deplete stock further, and `pnpm db:seed` does not restore it. The preflight stops a run whose starting shortfall is above 5%, but it checks only the stock at the start. Recreating the database is a manual, destructive step that the docs describe and the load generator never performs.
- **Worker backlog** is not part of the thresholds. At the offered rate, about 14 orders per second arrive; the worker runs 5 passes at a time by default. The M3 metrics `commerce_orders` and `commerce_worker_passes_total` show whether it keeps up.

## Packaging

- `apps/loadgen/src`: `config.ts` (Zod: `ORDERS_API_URL`, default `http://localhost:3000`), `random.ts`, `profiles.ts`, `plan.ts`, `runner.ts` (scheduler and HTTP), `stats.ts`, `preflight.ts`, `cli.ts` (the tested CLI logic), `index.ts` (the factory), and `main.ts` (the thin CLI entry, excluded from coverage). Each is built through factories with an injected clock, timers, random source and HTTP function.
- **Docker:** the root build includes the load generator, so the Dockerfile copies it into the build stage only. It is not part of the runtime image and has no Compose service.
- **Root script:** `"loadgen": "node --env-file-if-exists=.env apps/loadgen/dist/main.js"`, so arguments after `pnpm loadgen` pass through.
- **Workspace wiring:** a TypeScript project reference, and the new modules added to the coverage gate.
- **Telemetry:** none in the load generator. The API's existing spans and metrics show the traffic. Requests carry no `traceparent`, so each request is a new trace.
- **Invalid flags or config** exit with code 1 and a message naming the flag or variable, like the apps. An unknown profile lists the available ones.

## M5 integration

- `createLoadGenerator({ profile, seed, baseUrl, clock, timers, random, fetch })` returns `{ plan, planHash, run(): Promise<RunReport> }`. M5's scenario runner calls it in-process, with no CLI.
- Profiles are a closed registry. M5 may add profiles, such as bursts, each with its own golden hash test.
- An incident bundle's `manifest.json` records the profile, seed, plan hash and run prefix, so the traffic is part of the reproducible ground truth.
- The load generator stays fault-agnostic. Only the M5 fault package decides whether a fault is active.

## Test strategy

- **Deterministic, in CI with Vitest:** generator vectors, plan generation and its golden hash, the mix and parameter bounds, the scheduler on a fake clock and timers, accounting and percentiles, the preflight against stubbed responses, the catalog export, and config and CLI validation.
- **Functional, in CI:** a short run of 2 s at 20 rps, 40 entries with no warm-up, against the API built in-process with `buildServer`. The telemetry smoke test already imports the API this way.
  - **Isolated data:** it uses the test database from `TEST_DATABASE_URL`, `commerce_test`, never the Compose `commerce` database. Before the run it empties the order tables and products and inserts the seed catalog, as the existing API tests do, so stock is known and never depends on earlier local runs.
  - **Profile:** a test profile built from the same generator, passed to the factory directly and not registered in the CLI.
  - **No worker** runs, so orders stay `pending`. Reads still return 200, and no stock is reserved during the test.
- **Local only:** the performance check against the Compose stack. It creates real orders, so it runs only with the owner's approval, like the e2e scripts.
- **Not asserted:** exact latencies in CI, and worker throughput.

## Acceptance criteria

[D] is a deterministic test in CI. [L] is a local check against the Compose stack, run with approval. All M2 and M3 tests keep passing, unchanged.

1. [D] **Plan determinism.** For the same profile and seed, the canonical plan is byte-identical and the plan hash is equal across runs and processes. The `steady`/42 hash equals a committed golden value. A different seed gives a different hash. `--dry-run` prints the hash and makes no network call.
2. [D] **Plan contents.** Over the `steady`/42 plan: the operation mix is within 2 percentage points of 60/25/15; SKUs are drawn uniformly from the 1,000 catalog SKUs; every create has 1 to 3 distinct SKUs with quantity 1 or 2; payment methods are only `pm_card_ok` and `pm_card_declined`; every read targets a create scheduled at least 1 s earlier; and offsets equal `index * 1000 / 55`.
3. [D] **PRNG.** Fixed vectors for mulberry32 and splitmix32 stream derivation. Streams are independent: changing one dimension's draws leaves the others unchanged.
4. [D] **Catalog export.** `@commerce/db/catalog` returns exactly the seed's 1,000 products, `seed.ts` re-exports the same functions, and the built catalog module imports neither `pg` nor the pool module at runtime.
5. [D] **Idempotency.** Every create carries `<runPrefix>-<keyIndex>` within the API's key rules. Two runs use different prefixes and the same plan hash. A 200 replay or a 409 is counted as failed.
6. [D] **Open-loop scheduling.** On a fake clock, requests start at their offsets regardless of response latency. No more than 64 are in flight. An entry not started within 100 ms of its due time is missed and never sent. A read whose create failed, was missed or has not completed is skipped. No sent request is left pending at the end.
7. [D] **Accounting.** Every entry due in the window gets exactly one category from the table. Offered = sent + missed + skipped, and sent = successful + failed. Throughput, failure rate, miss rate, skip rate and nearest-rank percentiles use the denominators defined above. Timeouts count as failed at 5,000 ms. Warm-up and preflight requests are excluded.
8. [D] **Preflight.** Against stubbed responses: an orders API `/readyz` other than 200, a planned SKU missing from the catalog, or an aggregate stock shortfall above 5% each stops the run with exit 1 and a message, before any planned request is sent. The shortfall is computed exactly as defined above, including a boundary case at exactly 5%, which passes. The report lists every short SKU with its planned, available and unmet quantities in the specified order, both when the run passes and when it fails, and a run with short SKUs but an aggregate of 5% or less still passes. The preflight sends only `GET` requests, and none to the worker. `--dry-run` sends nothing.
9. [D] **Functional run.** A 2 s, 20 rps run against the in-process API, on the test database freshly seeded by the test, including the preflight: every sent request gets its expected status, created orders exist and can be read back, and there are no replays or conflicts. It never connects to the Compose `commerce` database.
10. [D] **Config and CLI.** An invalid profile, seed, URL or flag exits 1 with a message naming it.
11. [L] **Performance.** `pnpm loadgen --profile steady --seed 42`, against `docker compose up -d --build --wait` with the preflight passing, reports throughput of at least 50 rps, p95 under 200 ms and a failure rate under 1% over the window, and exits 0.
12. [D] **Quality gates.** Format check, lint, typecheck, build and the coverage gate pass, with each load-generator module at 80% line coverage or more. All M2 and M3 tests pass unchanged.
